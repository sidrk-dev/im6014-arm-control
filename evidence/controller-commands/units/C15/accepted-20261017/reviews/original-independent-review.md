Must fix:

1. [P2] End the exchange timer before waiting for the owner lock (arm_manual.py:1049-1054).
   - What this is: The finally block records completion of capture_exchange, including failed and cancelled exchange attempts.
   - Problem: It acquires self.lock before reading the ending clock. If an HTTP snapshot or input thread holds the lock when capture_exchange has already returned or raised, that unrelated post-exchange wait is included in transaction_latency_s and transaction_max_s. For example, an injected exchange advances the timing clock by 2 ms and completes while another thread holds arm.lock; advancing the clock by another 20 ms before releasing that lock makes this code record 22 ms for the completed 2 ms exchange.
   - Fix: Read the ending observation clock immediately on entering finally, before acquiring self.lock, with the same exception isolation used for the starting sample. Acquire the lock only to update StationTiming from those local start/end values. Preserve the original exchange exception and the unavailable-duration outcome.
   - If we skip it: The metric can attribute dashboard/input contention to transport latency, defeating the distinction between actual exchange latency and owner-loop scheduling delay. The existing synthetic-latency tests have no competing lock holder and cannot detect this case.
   - Parent check requested: Add and run a fake-only event-coordinated regression that holds arm.lock across exchange completion, advances the injected timing clock during that post-exchange wait, and asserts the recorded duration excludes the wait. Check both a successful exchange and a failing exchange while retaining the original failure. I did not execute this scenario.
