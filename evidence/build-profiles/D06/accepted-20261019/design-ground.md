Candidate A uses typed tool and transform configuration inside `BuildProfile`, with validation records holding a canonical configuration snapshot. Its caller supplies an explicit tool declaration and named mounting transform before recording an existing test result. The invalidator compares the selected typed configuration components against that snapshot.

The narrow type sketch is `ToolConfiguration(presence, identity, revision, status, source)`, `MountingTransform(name, parent_frame, child_frame, translation_m, rpy_rad, status, source)`, `ValidationDependency(kind, name)`, and `ValidationRecord(check_id, dependencies, profile_snapshot_json, reported_status, evidence_reference)`. Tool presence distinguishes unknown, explicitly absent, and attached. Unknown transforms have no translation or rotation values. Known transforms require both tuples, explicit frames, source, and verification status. No identity transform or nominal tool is supplied by default.

The transform convention must be stated exactly. One option is child coordinates mapped into the parent with `Rz(yaw) Ry(pitch) Rx(roll)` and a translation in meters. This represents a transform declaration without implementing kinematics. Equivalent angle descriptions can conservatively invalidate because D06 compares declarations. New tuple fields must reject mutable lists and nonfinite numbers. The JSON parser must reject duplicate keys and unsupported fields as the existing parser does.

The narrow API signatures are `record_validation(profile: BuildProfile, *, check_id: str, dependencies: tuple[ValidationDependency, ...], reported_status: ValidationStatus, evidence_reference: str) -> ValidationRecord` and `invalidate_validation(record: ValidationRecord, profile: BuildProfile) -> ValidationRecord`. A returned pending record clears its completed result fields. The snapshot is an immutable canonical string, so it cannot retain mutable caller containers.

This design gives tool and transform values explicit units and meaning. It also expands the profile schema, parser, constructors, serialization, and related compatibility obligations. An optional field must mean unknown, not identity or no tool. The repository explicitly requires tool mount configuration and source/status for uncertain values, so this is an appropriate future geometry shape. [Configuration requirements](/tmp/d06-codex-recovery-20261019/docs/ROBOT_WORKBENCH_AGENT_PROMPT.md:113). It is more implementation than pure D06 bookkeeping needs today.

Candidate B uses the parent's closed dependency enum and exact opaque configuration artifacts beside the existing profile. Its caller supplies `ConfigurationArtifact(data: bytes | None, source: str)` for tool and mounting configuration. A `ValidationContext` combines those with the existing `BuildProfile`. A record selects `PROFILE`, `TOOL`, `MOUNTING_TRANSFORM`, or a nonempty combination. The record binds the selected fingerprints when the caller explicitly reports a result.

The chosen narrow API signatures can remain `ValidationRecord(check_id: str, dependencies: frozenset[ValidationDependency])`, `ValidationRecord.record_result(context: ValidationContext, *, status: ValidationStatus, evidence: str) -> ValidationRecord`, and `ValidationRecord.invalidate_changed(context: ValidationContext) -> ValidationRecord`. Keep the status, evidence, fingerprint pairs, and any scope binding in frozen records. Pending records carry no completed result metadata. This preserves the parent's short call path and has no geometry parser, persistence engine, controller import, or owner integration.

I recommend B for the narrow exact-artifact contract, subject to the following corrections and explicit limits. It can satisfy D06 by tracking changes to supplied configuration declarations. It cannot detect an unrecorded physical change or validate the meaning of opaque transform bytes. The implementation and ledger should use that precise claim.

1. Bind every completed record to its build context. In the prototype, a TOOL-only record never fingerprints `context.profile`. The same artifact bytes and source can therefore retain PASSED for another robot, build, backend, or active joint set. [Context selection](/tmp/d06-evidence-20261019/validation_candidate.py:58). [Recorded fingerprints](/tmp/d06-evidence-20261019/validation_candidate.py:107). Add an unconditional scope fingerprint containing robot, build, backend, and ordered active and locked joint identities. Use PROFILE separately for conservative full-profile invalidation. Alternatively, require PROFILE for every record and document the resulting broader invalidation. The first option preserves category selectivity. Original profile revision and full digest can remain audit metadata without automatically treating every revision-only change as a selected dependency change. D05's exact revision binding must remain unchanged.
2. State who declares relevance. A reduction-dependent check must select PROFILE. A tool-pose check may need all three dependencies. An unrelated tool artifact change leaves a PROFILE-only record current, which is correct only if that check is genuinely independent of the tool. This library cannot infer physical dependencies from a check name. Use a documented dependency example set rather than imply that the enum discovers affected tests.
3. Define unknown narrowly and preserve uncertainty. `data=None` must block completed results for a selected tool or mounting dependency. Nonempty bytes mean a supplied configuration artifact, not measured geometry. PROFILE always has a digest even when it contains an unknown actuator identity, a declared mapping, or unknown measurements. [Prototype PROFILE fingerprint](/tmp/d06-evidence-20261019/validation_candidate.py:58). A software test about that document can have a caller-reported pass. A physical measurement claim still needs its own evidence and semantics. A blanket claim that every unknown physical fact forces every PROFILE check pending would be false for this design.
4. Keep result context claims honest. `record_result(current_context, status=PASSED, evidence=old_reference)` stamps the supplied current context. It cannot tell whether the referenced result actually ran with those inputs. [Result method](/tmp/d06-evidence-20261019/validation_candidate.py:107). This is acceptable only as an explicit caller report. If accepting independent test receipts is required, add a small receipt containing the tested context fingerprints, check ID, reported outcome, and evidence digest. Match that captured context before attaching the result. Do not claim that hashing arbitrary receipts certifies their contents.
5. An evidence string is a reference, not content binding. Replacing bytes at that location leaves the prototype's record unchanged. [Evidence fields](/tmp/d06-evidence-20261019/validation_candidate.py:69). Either document that limitation or accept immutable evidence bytes and store their digest separately from the reference. D05's artifact-content guarantee is stronger because it explicitly accepts bytes again during matching. [D05 artifact comparison](/tmp/d06-codex-recovery-20261019/calibration_binding.py:35).
6. Enforce deep immutable input values. The prototype correctly requires immutable artifact bytes, frozenset dependencies, and tuple pairs, and it rejects incomplete completed records. [Artifact boundary](/tmp/d06-evidence-20261019/validation_candidate.py:27). [Record boundary](/tmp/d06-evidence-20261019/validation_candidate.py:76). Its `isinstance` checks permit subclasses that can override fingerprint behavior or retain mutable fields. Reject subclasses for new public context and artifact records, or internally capture validated canonical strings and fingerprints before retaining them. The current parser provides a detached immutable value pattern to reuse. Avoid changing established D01-D05 contracts merely to support D06.
7. Preserve conservative canonicalization. Hash `profile.to_json()` as D05 does. Hash exact artifact bytes and their source using one deterministic internal encoding. Whitespace changes in an artifact or source changes intentionally invalidate. Bytes with equivalent geometric meaning need not compare equal. Sorting dependency pairs makes record equality deterministic. No additional JSON loader is necessary for opaque bytes, and none should be implied.
8. Pending is sticky only through the returned record sequence. The prototype returns a fresh pending record and clears evidence and hashes. [Invalidation](/tmp/d06-evidence-20261019/validation_candidate.py:118). Reverting configuration cannot complete that returned record without a new explicit result. The original immutable completed object still exists. The caller must retain the returned record as the current state. There is no runtime owner integration that enforces storage or prevents deliberate reuse of an older object.

Both alternatives keep D05 as exact calibration artifact binding and D06 as validation bookkeeping. Both reject transform defaults and treat missing relevant configuration as pending. Candidate A earns its larger shape when callers need to inspect or calculate transforms. Candidate B is the smallest complete change for supplied artifact invalidation, provided the context binding and terminology above are resolved.
